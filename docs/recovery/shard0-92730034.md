# Producer runbook — shard-0 target-sync to 92,730,034 (produce · verify · seal)

Internal team tool. This runbook takes the Aug 8 full shard-0 database offline
to the pinned target block **92,730,034** from a single verified donor bundle,
compacts it into a clean validator `harmony_db_0`, deeply verifies it, and
seals a checksummed release directory for devops to publish. It is the
optional clean-DB fallback behind the in-place recovery effort (in-place
handoff §2.4 / §10 gate 9).

The core correctness machinery — strict never-recovering read-only opens,
full offline replay with per-block BLS certificate verification, the strict
compactor, and the deep `verify-db` — is what makes the resulting DB
trustworthy. Everything is fail-closed; every phase writes a hash-chained
report.

## Settled storage layout (revision 11)

- **Donor** = `mhe-snaps0-01` (37.27.114.121), synced to abandoned-branch head `92,751,016` (epoch 3003), kept for forensics. It has a full DB retaining the range back to `92,591,098` and can be **stopped at will**. Never export from a live directory — stop it or take a crash-consistent snapshot first.
- **Replay working host** = a fresh instance spun up from the Aug 8 copy. The Aug 8 copy is consumed directly as the working copy; Storj backups are restorable at any time, so no custody ceremony is needed.
- Producer host: ~8 TB total, ~3.2 TB free, ≥16 cores / 64 GB RAM. Replay keeps its `--min-free-bytes` preflight.

Residual risk (operator-accepted, recorded here): the integrity layer is plain
SHA-256 (no signatures). It protects against corruption, mix-ups and stale
inputs — not against a motivated tamperer with filesystem access. Revisit if
this tool is ever adopted for validator-facing releases.

## The anchor manifest

Write `anchor.json` with the pinned values above (schema
`hmy-recovery-anchor-v1`; the field layout mirrors in-place §3.1) and its
`anchor.json.sha256` sidecar. `inspect-db`/`export-bundle` fill the
`FILL_AND_VERIFY` fields (state root, viewID, target certificate hash,
`ss<3002>` digest) as they run; reconciling those with the in-place effort is
a non-blocking §8 integration item.

## Phases

Set `RECOVERY_REPORT_DIR` to a durable directory; every wrapper writes its
report and `.sha256` there and refuses to run without it.

0. **Donor preflight** (cheap, mechanical — availability already confirmed):

   ```sh
   scripts/recovery/30-export.sh --report-only   # export-bundle --report-only against mhe-snaps0-01's cold copy
   ```

1. **Inspect both Aug 8 copies + agreement** (`scripts/recovery/10-inspect.sh`):
   full state + off-chain digests, preimage coverage required, full-archival
   replay preflight, baseline gate, then `--compare-with` for the two-copy
   agreement verdict. Replay consumes the passing verdict.

2. **Export the bundle** (`scripts/recovery/30-export.sh`): single-donor
   block+certificate export, per-block BLS verification, parent-hash chain
   terminating at the pinned target hash, abandoned-child certificate sidecar,
   chunked with `SHA256SUMS`.

3. **Replay into the working copy** (`scripts/recovery/40-replay.sh`):
   checksum gate on every input, exact-range bundle consumption, per-record
   validate-then-insert with certificate persistence to `block-sig-N`,
   runtime-metadata cleanup, the strict finalizer (pending-queue clear, trie
   commit, preimage flush, durable close), then the reopen gate. Leaves the
   journaled `COMPLETE_VERIFIED` 4.7 TB working DB on the producer host as the
   compaction source and evidence (not packaged).

4. **Compact** (`scripts/recovery/50-compact.sh`): strict trie-sync state copy
   into a fresh `harmony_db_0`, canonical retention window with per-block
   certificates, off-chain tables (validator stats omitted, pending queues
   omitted — in-place §2.2), all four heads at the pinned target hash, the
   marker-excluded logical digest, and the recovery-completion marker. Internal
   mode by default (`internal:none`); pass `--metadata-reference-manifest` for
   the in-place convergence proof. 200 GB size gate.

5. **Verify** (`scripts/recovery/55-verify.sh`): read-only deep verification —
   four-heads-at-target, mode-aware marker checks, exact block-sig verification
   across the whole retained window, full state traversal, off-chain set
   equality, no fork/future/rejected-shard-1 keys, unresolved bare-hash32 keys
   fatal, logical digest cross-checked against the marker.

6. **Seal** (`scripts/recovery/60-package.sh`): single-invocation
   `package-db` — stage under a held storage lock, fully re-verify, journaled
   atomic promote, `SHA256SUMS` + `release.json` + `INSTALL.md` + `READY` last.
   Prints the devops publish handoff.

Each phase's report chains the SHA-256 of every input it consumed:
`anchor → inspect → agreement → bundle manifest → replay.json → compact.json →
verification.json → release.json`. A mutating command refuses inputs whose
recomputed SHA-256 disagrees with the recorded chain value.

## Gate checklist (all must hold before sealing)

- inspect: heads agree, head < target, no known-bad at/below head, full-archival preflight passes, two-copy agreement `agreed`.
- replay: three heads == pinned target hash, target certificate verified from the exact key, gate `passed`, journal `COMPLETE_VERIFIED`.
- compact: destination DigestSet == replay's, four heads written, marker written, size ≤ 200 GB, journal `COMPLETE_VERIFIED`.
- verify: `passed`, `certificates_verified == 29364`, logical digest == marker == `compact.json`.
- package: `SHA256SUMS` re-verifies from the sealed root, `READY` content == release ID, journal `COMPLETE_VERIFIED`.

## Failure table (journal states)

| Symptom | State | Action |
| --- | --- | --- |
| crash/error during any mutating phase | `IN_PROGRESS` | discard the destination and rebuild (v1 no-resume) |
| clean build over the 200 GB gate | `COMPLETE_UNRELEASABLE` | preserved for diagnosis; operator retention decision; `package-db` refuses it |
| `package-db` killed after promote, before `READY` | substate `PROMOTED`, `READY` absent | rerun re-verifies the unsealed dir and seals, or quarantines a tampered one |
| `package-db` killed after `READY`, before terminal record | substate `SEALED`, `READY` present | rerun re-verifies the sealed dir and completes the journal |

## Devops publish handoff

`package-db` prints the sealed release directory and a short "how to publish"
note (transfer the whole tree with `rclone --checksum`, preferably `READY`
last so a partial upload is never mistaken for complete; consumers verify via
`SHA256SUMS` either way). Upload execution and endpoints are devops-owned and
explicitly out of this plan's scope.

## Adoption-time step (not a producer gate)

Booting the actual `v2026.1.2-recovery` binary against the sealed artifact is
the in-place agents' adoption-time rehearsal (their §10 gate 9). CI covers the
stock-binary offline boot smoke only (`scripts/recovery/e2e-localnet.sh`).
